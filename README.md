# Место встречи

«Место встречи» — бот для MAX, в котором школьники ищут мероприятия и людей со схожими интересами, а педагоги предлагают свои события. Это наш школьный проект, который мы постепенно дополняем и дорабатываем.

Этот README — **для тех, кто работает с кодом**. Здесь собраны устройство проекта, запуск, основные правила и подсказки, куда смотреть, если нужно добавить функцию. Все подробности интерфейса находятся в самом коде.

## Как всё работает

Бот написан на Python 3.12 и использует библиотеку `maxapi`. Он получает сообщения через Long Polling, обрабатывает команды и нажатия на кнопки, а данные хранит в SQLite.

Главная точка входа — `bot.py`. В нём находятся меню, обработчики сообщений и кнопок. Остальная логика разнесена по модулям: так проще искать нужную функцию, чем разбираться в одном очень большом файле.

При запуске Docker сначала выполняется `import_events.py`, затем запускается `bot.py`. База лежит в `/data/events_v2.db` внутри контейнера; Docker-том сохраняет её между перезапусками.

Если добавляете новый файл Python, не забудьте импортировать его там, где он используется.

## Как запустить

Нужны Git, Docker Desktop и токен бота MAX. Работаем в PowerShell из папки проекта. Docker Desktop должен быть запущен.

```powershell
cd "C:\Users\MSI\Place-meeting"
docker build -t place-meeting-bot .
```

Устанавливаем токен и свой код модератора **только в текущей консоли**, не записываем их в исходники:

```powershell
$env:MAX_BOT_TOKEN = Read-Host "Токен MAX"
$env:MODERATOR_ACCESS_CODE = Read-Host "Код модератора (не короче 12 символов)"
```

Запуск контейнера:

```powershell
docker rm -f place-meeting
docker run -d --name place-meeting --restart unless-stopped `
  -v place-meeting-data:/data `
  -e MAX_BOT_TOKEN `
  -e MODERATOR_ACCESS_CODE `
  place-meeting-bot
```

Если контейнер ещё не существовал, ошибка от `docker rm` не страшна. Проверяем, что всё запустилось:

```powershell
docker ps
docker logs --tail 50 place-meeting
```

Для текущей версии Docker-образа используются сертификаты `root.cer` и `sub.cer` **только если они есть** рядом с Dockerfile. Если без них у вас не проходит SSL-подключение к MAX, добавьте полученные ранее сертификаты перед сборкой. Сертификаты и токены в Git не отправляем.

### Обновление после изменения кода

После правок в Python-файлах нужно пересобрать образ и пересоздать контейнер:

```powershell
docker build -t place-meeting-bot .
docker rm -f place-meeting
docker run -d --name place-meeting --restart unless-stopped `
  -v place-meeting-data:/data `
  -e MAX_BOT_TOKEN `
  -e MODERATOR_ACCESS_CODE `
  place-meeting-bot
```

Переменные `$env:MAX_BOT_TOKEN` и `$env:MODERATOR_ACCESS_CODE` должны быть заданы в этом окне PowerShell. Если окно закрывали, введите их снова.

## Как устроен `bot.py`

У нас есть три основных типа обработчиков:

- `@dp.message_created(Command('start'))` — реагирует на команду `/start`. Аналогично устроены `/catalog`, `/people`, `/profile`, `/filters` и `/moderator`.
- `@dp.message_callback()` — обрабатывает нажатия на инлайн-кнопки. Там берётся `payload` кнопки и передаётся в функцию `dispatch(uid, parts)`.
- `@dp.message_created(F.message.body.text)` — получает обычный текст: например, ответ при заполнении анкеты, ссылку или сообщение другому участнику.

**Пример:** кнопка с `payload='profile'` попадает в общий обработчик нажатий, затем `dispatch()` выбирает нужный экран. Новую кнопку мало просто нарисовать: для её `payload` нужно добавить действие в обработчик.

Для клавиатур уже есть функции `b()`, `keyboard()` и `ui()`. Лучше пользоваться ими, а не собирать клавиатуру заново в каждой функции. Там, где возможно, бот редактирует предыдущее сообщение вместо отправки множества новых.

Обработчики должны быть объявлены **до** `asyncio.run(dp.start_polling(bot))`, иначе они не будут зарегистрированы при запуске.

## Как работать с базой

Для запросов используем `connect()` из `catalog.py`:

```python
from catalog import connect

with connect() as db:
    events = db.execute("SELECT id, title FROM events LIMIT 5").fetchall()
```

`connect()` возвращает соединение, которое закрывается после блока `with`. Это особенно важно на Windows: иначе временная база может остаться занятой другим процессом.

Таблицы отдельных функций создаются через `init()` соответствующих модулей при запуске бота. Если добавляете поле в существующую таблицу, помните, что база у уже запущенных пользователей **не пустая**. Новую схему нужно делать совместимой со старыми данными, а не просто удалять таблицу и создавать её заново.

Наш основной Docker-том — `place-meeting-data`. Не удаляйте его при обычном обновлении. Перед изменениями, затрагивающими анкеты, заявки или таблицы базы, полезно сделать копию:

```powershell
docker cp place-meeting:/data/events_v2.db .\events_v2_backup.db
```

Копию лучше делать после остановки контейнера, чтобы данные не изменялись во время копирования.

## Что учитывать, когда добавляешь функцию

1. Сначала определите, в каком модуле должна быть логика. Кнопку или команду подключайте в `bot.py`, а работу с данными — в подходящем файле.
2. Проверяйте входные данные: даты, ссылки, длину текста, идентификаторы из `payload`. Нельзя считать, что любой пришедший `payload` корректен.
3. Не показывайте чужие анкеты без согласия владельца. Не передавайте контакты автоматически и проверяйте блокировки перед общением.
4. Модераторские действия должны проверять права **на серверной стороне**, а не просто скрывать кнопки. Роль педагога и статус подтверждённого педагога — разные вещи.
5. Смена роли через модератора удаляет данные прежней роли. Не меняйте этот процесс без обсуждения с командой и копии базы.
6. Если обработчик обращается к MAX, он должен оставаться асинхронным. Не добавляйте долгие синхронные операции в обработку кнопок.

В проекте есть небольшой кэш для ускорения каталога. Если меняете данные мероприятий, учитывайте, что кэш может потребоваться обновить. Не добавляйте новые кэши без необходимости: из-за них становится сложнее понять, почему данные не обновились.

## Как проверить свои изменения

После правок сначала проверяем синтаксис:

```powershell
python -m py_compile bot.py catalog.py profiles.py people.py social.py `
  teacher_events.py role_requests.py direct_messages.py filters.py `
  favorites.py taxonomy.py import_events.py
```

Затем пересобираем Docker, смотрим логи и проверяем нужный сценарий в MAX. Например: `/start` → анкета → публикация → поиск людей → заявка → решение по заявке. Для функций модератора лучше использовать тестовые аккаунты.

Отдельных тестовых скриптов в чистой сборке нет. Поэтому успешная проверка синтаксиса **не означает**, что всё работает в MAX. Если бот перезапускается, смотрите `docker logs --tail 100 place-meeting`; если кнопка ничего не делает — сначала проверьте её `payload` и соответствующую ветку в `dispatch()`.

## Если что-то не работает

**Контейнер не запускается:** `docker ps -a` и `docker logs --tail 100 place-meeting`. Проверьте, что задан `MAX_BOT_TOKEN`.

**Изменения не появились:** скорее всего, образ не был пересобран или запущен старый контейнер.

**Бот не видит мероприятия:** проверьте `events.json`, работу `import_events.py` и том `/data`.

**Проблема с сертификатами:** проверьте, нужны ли для вашего подключения `root.cer` и `sub.cer`, и пересоберите образ после их добавления. Не отключайте проверку SSL ради обхода ошибки.

**База данных занята:** убедитесь, что соединения открываются через `with connect() as db`, а не остаются висеть после запроса.

### Поиск мероприятий по тегам

Если выбрано несколько тегов, бот показывает мероприятия, у которых совпал **хотя бы один** тег. В начале списка идут мероприятия, совпадающие с наибольшим числом выбранных тегов. Если совпадений одинаковое количество, раньше показывается мероприятие с более близкой датой. Например, при выборе «Комедии» и «12–15 лет» комедии без возрастного тега тоже будут в результатах, но после мероприятий с обоими тегами.

Место, дата и формат работают как обычные ограничения: если указать конкретный город или формат, неподходящие мероприятия не появятся.

## Выбор даты в фильтре

В меню «📅 Когда хочешь пойти?» можно выбрать только один период. На кнопках даты нет галочек. После выбора бот снова показывает этот экран с подписью «Выбранная дата: ...». При вводе своей даты она отображается как ДД.ММ.ГГГГ. Чтобы убрать выбор, нажмите «✕ Сбросить дату».

## Одно рабочее сообщение в чате

В интерфейсе бот использует одно рабочее сообщение с кнопками на пользователя:

- При первом `/start` бот отправляет сообщение с меню.
- Когда пользователь нажимает кнопки, открывает фильтры, анкету или каталог, бот **редактирует это же сообщение**, а не отправляет новое.
- После ввода города, возраста, даты или других данных бот тоже меняет рабочее сообщение.
- ID рабочего сообщения хранится в таблице `ui_messages` базы SQLite, поэтому при перезапуске Docker бот продолжает использовать тот же экран.
- Если старое сообщение удалили и MAX сообщает об этом, бот создаёт новое рабочее сообщение.
- Уведомления о сообщениях, заявках, решениях модератора и действиях других людей приходят **отдельно**. Это важно, чтобы пользователь их не пропустил.

### Удаление старых рабочих сообщений

Когда бот вынужден создать новый рабочий экран, он сохраняет ID предыдущего экрана в таблицу `old_ui_messages` и пытается удалить старое сообщение через `bot.delete_message()`. При следующих действиях бот проверяет эту таблицу и повторяет попытку для тех сообщений, которые ещё не удалены. Актуальный экран не удаляется.

**Ограничение MAX:** в личном диалоге бот не может получить всю историю сообщений, как администратор группового чата. Поэтому он удаляет только **те старые рабочие сообщения, ID которых уже известны и сохранены**. Сообщения бота, созданные до появления учёта ID, автоматически найти и удалить нельзя. Сообщения пользователя и отдельные уведомления бот не трогает. Если MAX запрещает удаление, сообщение останется.

Для защиты от лимитов MAX между удалениями добавлена короткая пауза.

**Установка:** обнови `bot.py`, пересобери Docker-образ и пересоздай контейнер, подключив тот же том `place-meeting-data:/data`. Перезапуск старого контейнера без пересборки не применит код.

## Если команда /start не показывает экран

Текстовые команды (`/start`, `/catalog`, `/filters`, `/people`, `/profile`, `/moderator`) создают новый рабочий экран **внизу чата**. Предыдущий сохранённый экран бот пытается удалить. Нажатия кнопок редактируют текущий экран, поэтому история не засоряется.

Если бот не отвечает, проверяем ошибки **после команды**:

```powershell
# Отправьте /start в MAX, затем выполните:
docker ps -a
docker logs --since 2m place-meeting
```

Если контейнер постоянно перезапускается или в логах есть исключение, дело не в оформлении рабочего экрана. Пришлите текст исключения без токена MAX.

## Верификация педагогов

У педагога нет отдельной ученической анкеты. В меню есть кнопка подтверждения статуса.
Он последовательно вводит ФИО, место работы и должность, затем отправляет ссылку на документ.
Черновик хранится в `teacher_verification_drafts`, а полная заявка — в `teacher_checks`.
Модератор видит четыре поля и принимает или отклоняет заявку по прежней схеме.
После подтверждения ФИО, место работы и должность записываются в профиль для каталога и
сообщений; педагог становится доступен в поиске без возраста, интересов и навыков.
При смене роли данные педагога удаляются.


ФИО, место работы и должность могут относиться к персональным данным. Доступ к заявкам ограничивайте модераторами, не публикуйте базу или ссылку на документ.


## Исправления после замечаний (7 ноября 2026)

- В фильтре даты выбор любого готового варианта сразу возвращает на экран «Настроим поиск!» с сохранённой датой.
- В меню заявок «Входящие» и «Отправленные» показываются только при наличии соответствующих активных заявок; пустые разделы скрыты.
- Подтверждение педагога: ФИО, место работы, должность и ссылка на документ; модератор видит эти сведения. У педагога нет отдельной анкеты ученика.
- Когда модератор вводит причину отклонения педагога, на экране остаётся только «Назад»; старые кнопки подтверждения/отклонения игнорируются до завершения ввода.
- Добавление мероприятия идёт по шагам на русском языке: название, описание, дата, место, формат, тематика, ссылка. После заполнения показывается предпросмотр, затем «Отправить на проверку», «Изменить» и «Назад». В редактировании можно выбрать отдельное поле, а после ввода возвращаться в меню редактирования.

Не удаляйте Docker volume `place-meeting-data`: в нём сохраняются анкеты, заявки и мероприятия. После замены файлов нужно пересобрать образ и **пересоздать** контейнер.

- Педагог выбирает **формат** мероприятия кнопками: «Офлайн» или «Онлайн». Выбор ровно один.
- **Тематика** выбирается через категории «Вид искусства», «Возрастная категория», «Музыкальные» и «Активности». Можно отметить несколько пунктов и нажать «✅ Готово». При редактировании события выбор возвращает на экран «Что Вы бы хотели изменить?».
- Кнопки редактирования: «Название», «Описание», «Дату», «Место», «Формат», «Тематику», «Ссылку», «◀️ Назад», «✅Готово».
- Все разрешённые теги определяются в `event_tags.py` по документу «Тэги мероприятий.docx». Старые названия («Пешеходные экскурсии», «волонтёрство», «Детям от 12 до 15 лет») приводятся к новым. В `events.json` исходные метки приведены к списку из документа; четырём мероприятиям с общей меткой «мероприятие» присвоена категория по очевидному типу события из его названия или места проведения.
- При обновлении контейнера **не удаляйте Docker-том `place-meeting-data`**: там находится база.

## Стабилизация кнопок (задача №1, пункты 28 и 10)

Кнопка изменяет **сообщение, в котором она находится**. Уведомление хранится
отдельно от меню и становится рабочим экраном только после нажатия. Предыдущий
рабочий экран удаляется в фоне; сообщения пользователя и остальные уведомления
не удаляются. Команды и ответы на текстовый ввод создают новый экран внизу диалога.

Для каждого сообщения сохраняется версия клавиатуры в новой таблице
`ui_callbacks`. Повторные нажатия прежней версии игнорируются. Весь переход
одного пользователя выполняется последовательно, включая изменение состояния.
Другие пользователи имеют свои блокировки. Long Polling и SQLite сохранены.
Запускайте **один процесс бота** на базу: блокировки действуют внутри процесса.

После обновления откройте `/start`: кнопки, отправленные старой версией приложения,
без версии клавиатуры не принимаются. Существующие анкеты, заявки и мероприятия
не удаляются миграцией. Перед обновлением остановите прежний процесс и сохраните
резервную копию SQLite вместе с её WAL/SHM, если они есть.

При ошибке изменения сообщения бизнес-действие автоматически не повторяется:
оно уже могло сохраниться в SQLite. Бот предлагает `/start`. Новый экран вместо
исчезнувшего создаётся только при HTTP 404; ошибки 403/429/5xx не считаются
доказательством удаления. При сбое удаления ID остаётся для следующего перехода.
Удаление может произойти позже отображения нового экрана. При недоставленном
ответе API нельзя гарантировать отсутствие уже отправленного сообщения.

Проверки без токена и внешней сети (Python 3.12):

```sh
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python -m compileall -q .
docker build -t place-meeting-navigation .
docker run --rm --network none --entrypoint python place-meeting-navigation -m unittest discover -s tests -v
```

Тесты сами задают фиктивный токен, используют временную БД и mock транспорта;
это не проверка реального MAX. Для корпоративного HTTPS-прокси сборки можно
передать доверенный CA bundle (с обычными системными корнями) через BuildKit:
`docker build --secret id=build_ca,src=/path/to/ca-bundle.crt -t place-meeting-navigation .`.
CA используется только при установке Python-зависимостей и не попадает в образ.
Это не меняет доверие сертификатам MAX во время работы контейнера.

Диагностика при обычном запуске `python bot.py`: записи `callback_ack`,
`callback_logic`, `callback_total`, `api operation=…`, `db`, `cleanup` содержат
время в миллисекундах. Логи приложения не содержат payload, токен, ID пользователей,
текст переписки или тело ошибок API. `db` измеряет время соединения/транзакции,
а не отдельный SQL-запрос. `callback_total` включает ожидание блокировки; время
доставки события от MAX до обработчика этим способом не измеряется.

Причины, подтверждённые исходным кодом: предпочтение сохранённого ID вместо
нажатого; удаление до 10 экранов с паузами по 0,55 с внутри блокировки;
изменение бизнес-состояния вне блокировки; незапущенное подтверждение callback
во время синхронной работы `dispatch`; отсутствующий `await` при начале
верификации педагога. Задержки внешней сети и влияние SQLite под нагрузкой
требуют замеров; они не объявляются причиной без данных.

Контракты проверены по исходникам установленной `maxapi==1.2.3`: `event.answer()`
вызывает `POST /answers`, `edit_message(message_id=…)` — `PUT /messages`,
`delete_message(message_id=…)` — `DELETE /messages`; ID отправленного сообщения
находится в `result.message.body.mid`. Используются обычные inline callback-кнопки;
к payload добавляется версия с проверкой предела 256 байт. Подтверждение не содержит
нового текста, редактирование выполняется отдельным запросом.
Официальные страницы `https://dev.max.ru/docs-api` недоступны в данном окружении
(403 прокси), поэтому соответствие последней редакции документации не подтверждено.

Перед выпуском вручную проверьте в MAX: каталог и избранное, быстрый двойной клик,
старую кнопку после перехода, уведомления дружбы/переписки/модерации при открытом
меню, ввод анкеты, `/start`, два аккаунта одновременно, восстановление после
перезапуска и ошибки сети. Сначала используйте тестовую БД и контролируемый бот.
Нужны реальные замеры `api`/`db`/`callback_total`, прежде чем обещать скорость.

Проверка этой правки: 24 автоматических теста на Python 3.12 прошли;
синтаксис проверен `compileall`, пробелы — `git diff --check`.
Сборка образа прошла с доверенным CA прокси через `build_ca`.
В облачном окружении дополнительно потребовались `--network host`,
`--add-host proxy:<адрес прокси окружения>`, `--build-arg HTTP_PROXY` и
`--build-arg HTTPS_PROXY`. Это настройки конкретной инфраструктуры, а не MAX.
Те же 24 теста прошли внутри собранного контейнера с `--network none`, от UID 65534.
Отдельно проверены импорт событий в временную БД, инициализация схемы и запуск
точки входа с подменённым `Dispatcher.start_polling`; реальный polling не запускался.
Dockerfile также разрешает непривилегированному пользователю чтение скопированного
кода, а `.dockerignore` сохраняет тесты для проверки образа.

## Задача №2: жалобы и модерация мероприятий

Исправлены пункты 11, 25, 27 и связанные уведомления из документа PM.
Основа — навигация первого этапа (`81ba22f`), Long Polling и `maxapi==1.2.3`.
Приложенная книга MAXapi использована как справочник; реальный MAX не вызывался.

Что было неверно:

- `social.py`: блокировка пары была бессрочной, повторная жалоба создавала ещё одну запись.
- `direct_messages.py`: жалоба удаляла последние сообщения; запуск удалял сообщения старше 30 дней.
- `bot.py`: адресат жалобы не получал обязательного уведомления; скрытые события исчезали из управления модератора, статусы педагога не учитывали видимость.
- `teacher_events.py`: не проверялось владение редактируемым событием, одобрение снимало скрытие, новая публикация с чужим URL перезаписывала существующую запись. Чтение заявки перед записью позволяло двум модераторам применить одно решение.

Теперь жалоба атомарно прекращает дружбу и разговор, отменяет ожидающие заявки
между участниками и блокирует общение в обе стороны на 7 дней. Автор получает
подтверждение текущим экраном, адресат — отдельное уведомление с именем автора,
причиной и сроком. Имя ученика уточняется по данным пользователя в событии MAX;
подтверждённое ФИО педагога сохраняется. Повторная жалоба во время блокировки
не создаёт запись и не продлевает срок. После истечения срока блокировка перестаёт
действовать, но дружба автоматически не восстанавливается. Все существующие пути
отправки проверяют блокировку. Уже отправленный в сеть запрос отозвать нельзя.

Модель мероприятий остаётся простой:

- `events` — текущая опубликованная версия, исходный ID, видимость `published` / `hidden`.
- `proposed_events` — черновик/заявка с `event_id` для правок или без него для нового события.
- Пока заявка `pending`, каталог показывает прежнюю версию, педагог — «На рассмотрении».
- Одобрение правок обновляет существующую строку, не меняя видимость; отклонение её не трогает.
- Скрытое событие доступно модератору для восстановления. Избранное остаётся в базе;
  после восстановления карточка снова видна. Список модератора разбит на страницы.
- «Мои мероприятия» показывает одну карточку на событие, последний запрос и замечания.
  После отклонения правок статус остаётся «Опубликовано» или «Скрыт», замечание доступно в карточке.
- Конфликт URL или владельца при одобрении оставляет заявку на рассмотрении и выводит
  модератору сообщение. Чужая карточка не перезаписывается. Нужно отклонить заявку с
  объяснением и попросить педагога исправить её.

Миграции выполняются автоматически и повторяемо, без очистки данных:

1. `interactions_blocked.expires_at` — срок в UTC. Для старой блокировки берётся
   дата последней жалобы + 7 дней. Если дата отсутствует/не читается — 7 дней
   от миграции; это консервативное правило, такие старые записи стоит проверить вручную.
   Поэтому давно истёкшие блокировки могут сразу перестать действовать.
2. `events.owner_id` — владелец по однозначной истории опубликованных заявок.
   У импортированных событий и записей с несколькими предполагаемыми владельцами
   поле остаётся пустым: модератор может менять видимость, но педагог не получает
   право редактирования наугад. Неоднозначности требуют ручного разбора истории.

`BEGIN IMMEDIATE` защищает решения модераторов, отправку заявок и жалобы; проверка
состояния и связанные записи выполняются в одной транзакции. Пользователи, события,
заявки, избранное и сообщения миграцией не удаляются. Автоматическая очистка старых
личных сообщений при старте убрана; срок их хранения теперь требует отдельного решения.
Новые зависимости не добавлены. Один процесс бота на базу по-прежнему необходим
для блокировок навигации; транзакции дополнительно защищают решения по заявкам.

Проверки: `python -m unittest discover -s tests -v` — 40 тестов, включая старые
сценарии навигации, жалобы и уведомления, границу 7 дней, старую схему и повторную
миграцию, сохранение переписки, скрытие/восстановление/избранное, новые публикации,
правки и отклонение, конфликт URL, чужого владельца и двух модераторов одновременно.
Временная SQLite и mock MAX; реальные токены не нужны.

Перед обновлением остановите бот и сделайте резервную копию тома
`place-meeting-data:/data`. Том не удаляйте и не запускайте `docker compose down -v`.
Сначала проверьте миграцию на копии базы. В MAX вручную проверьте жалобы через
обычный разговор и личное сообщение (включая свободную причину), уведомления обоим
участникам, имена, кнопки уведомлений при открытом меню, скрытие во время модерации
правок и повторное появление избранного. Отдельно проверьте старые записи с неизвестным
владельцем. Доставка уведомлений при сетевой ошибке не гарантируется: состояние в
SQLite сохраняется, ошибка логируется, автоматического повторения доставки нет.

Docker-образ собран с TLS-проверкой. Тесты также выполнены в контейнере с
`--network none`; запуск точки входа проверен с имитацией polling и временной БД.

## Задача №3: анкеты, интерфейс и даты

Анкета впервые заполняется по шагам город → возраст → интересы → навыки.
Каждый шаг создаёт новый экран; выбор внутри категории редактирует текущий.
Выбор интересов/навыков хранится в `user_workflows.data` до общего «Готово».
Переход «Готово» внутри категории лишь возвращает к категориям. Лимит — 10;
пустой профильный выбор применить нельзя. Редактирование заполненной анкеты
сохраняет выбор конкретного поля. Миграций и новых зависимостей нет.

`presentation.py` содержит общий Markdown-рендер карточки и работу с датами.
`format="markdown"` передаётся только для карточек; пользовательские символы
экранируются. Заголовки `#`/`###` и курсив заданы по PM. Официальный сайт MAX
в окружении отвечает 403 прокси; параметр режима проверен по maxapi 1.2.3,
приложенная книга использована как справочник. Внешний вид Markdown необходимо
проверить в MAX. Длинные поля карточки сокращаются для лимита сообщения;
исходные данные в SQLite не обрезаются.

Ввод дат педагогом: ДД.ММ.ГГ, ДД.ММ.ГГ ЧЧ.ММ, ДД.ММ.ГГ - ДД.ММ.ГГ.
Годы трактуются как 2000–2099, проверка прошлого — по Asia/Barnaul (UTC+7).
В базе новые даты хранятся в ISO; старые записи не переписываются. Непонятные
старые даты показываются текстом, ошибочные даты не роняют фильтр. При фильтре
по дате сначала идут события с конкретным днём, затем диапазоны и неопределённые.

Поиск показывает только школьников. В переписке видны подтверждённые данные
педагога. Меню, уведомления, двухуровневые выборы и тексты приведены к PM.
Для скрытых мероприятий сообщение об одобрении сохраняет уточнение о скрытии;
для отклонённых правок — о сохранении прежней версии (требования второго этапа).

Проверка: 60 unittest-тестов с временной SQLite и mock MAX, включая 40 тестов
предыдущих этапов; compileall и git diff --check. Реальные токены не использовались.
Ручная проверка: пройти анкету, лимит/отмену/категории, имена, карточки и Markdown,
меню обеих ролей, уведомления и даты в MAX; проверить на копии рабочего тома
совместимость существующих анкет, заявок и избранного. Автоматические тесты
не проверяют отрисовку клиентом MAX и реальную доставку уведомлений.
Все 60 тестов также прошли внутри Docker с `--network none`. Образ собран;
инициализация каталога, схемы и точки входа проверена с имитацией polling.

## Первое открытие бота

Кнопка «Заявки» в меню ученика открывает входящие заявки, а если их нет —
отправленные. Если список опустел, показывается другой активный раздел либо
сообщение об отсутствии заявок. Переходы проверены в `tests/test_requests.py`.

Команда `/role` открывает интерфейс заявки на смену роли для школьника и педагога:
нажмите «Написать модератору» и укажите причину. До одобрения текущая роль
сохраняется. При уже поданной заявке команда показывает её статус.
Кнопка «Сменить роль» из главного меню убрана. Для пользователя без роли
`/role` показывает первоначальный выбор роли.

После нажатия системной кнопки MAX «Начать» событие `bot_started` показывает
приветствие с inline-выбором роли. Писать `/start` для этого не требуется.
Само открытие окна чата не гарантирует событие от MAX. Для зарегистрированного
пользователя оба способа открытия показывают главное меню, без повторного выбора роли.
Команда `/start` остаётся способом вернуться к боту и восстановиться после сбоя.

Повторные/устаревшие `bot_started` отсекаются по `timestamp`, который сохраняется
в существующем `user_workflows.data`; схема БД не меняется. Новое системное событие
использует текущий экран. Быстрые повторные открытия в пределах трёх секунд
редактируют его; обычный `/start` позже создаёт экран внизу чата с фоновой очисткой.
Используются прежние блокировки и версии клавиатур. Метка события записывается
до отправки: при таймауте доставка могла состояться, поэтому событие не отправляется
повторно автоматически. Если приветствие не пришло, используйте `/start`.

Контракт проверен по README официального репозитория
https://github.com/max-messenger/max-botapi-python и исходникам установленной
maxapi 1.2.3 (`BotStarted.user`, `timestamp`, `chat_id`, `Dispatcher.bot_started`).
Сайт dev.max.ru в окружении отвечает 403 прокси.

Проверка: 68 тестов с mock MAX и временной SQLite. В MAX вручную: новым аккаунтом
нажать «Начать», проверить приветствие и обе кнопки; выбрать роль и вызвать `/start`,
проверить главное меню; повторить старт и быстрые нажатия, убедиться в отсутствии
одинаковых приветствий и сохранении работы остальных экранов. Реальная доставка
и поведение системной кнопки в клиентах MAX автоматическими тестами не проверены.
